Minibus · v1.29.0

Audit Brief

A Sunday minibus service for a Liverpool church: two routes, two buses, volunteer drivers, and a congregation that needs to know where the bus is. This is the orientation you would otherwise have to reverse-engineer.

For an independent reviewer Scope three apps, one spreadsheet Stack static HTML · Apps Script · Google Sheets
Architecture

The shape of it

Three clients share one Google Sheet and nothing else. There is no server, no database, no user table and no session. Apps Script is a thin request handler in front of the spreadsheet; the spreadsheet is the system of record. Everything a reviewer might expect to find in a backend either lives in a tab or does not exist.

Both clients are single-file progressive web apps — markup, styles and script in one document — installable to a home screen and functional with no signal. Each has its own service worker, scoped to its own folder, with separate cache namespaces.

Why it is built this way

The coordinator is a volunteer, not an operator. The spreadsheet is the artefact he already understood before any of this existed, and it is the one that survives the software. Every design decision that looks primitive — polling, no accounts, a tab as a queue — buys the property that the whole system can be read, corrected and operated from a spreadsheet by someone who does not code.

End to end

One journey

A driver pulls up at a stop and taps Picked up. Roughly twenty seconds later a phone at the next stop counts down differently. Everything between those two moments, in order.

Phone
0 ms

The tap is checked before it is a fact. Refused if the bus is moving (GPS speed, never transmitted); challenged if the run is under a minute old, or if less than half the timetabled leg has elapsed. A second tap within twelve seconds overrides — the driver is never locked out of his own record.

tripTap · tripMoving · tripTooSoon
Phone

Written to a local queue first, then sent. The timestamp is corrected by the difference between this phone's clock and the server's, learned from every successful call. A phone an hour out would otherwise poison every offset it sent, undetectably.

tripQueue · tripNow · tripSkew · fleet.trip.queue.v1
Script
1–2 s

Token checked, script lock taken. Existing rows for this run are indexed by event|stopId, so a resend, a double tap or a retry after a timeout collapses onto the same row rather than appending a second one.

doPost · handleTrip · handleTripLocked
Sheet

One row in Trip Events: run id, Sunday, route, driver, event, stop, scheduled time, actual time, offset, status, registration. The offset — minutes late or early — is computed at write time against the timetable, so the arithmetic is auditable in the sheet without running anything.

Script

The sheet is flushed, the write is stamped, then the cached run state is dropped — in that order. Any other order lets a reader that started before the write repopulate the cache with a state that predates it.

SpreadsheetApp.flush · stampTripWrite · dropTripCache
Passenger
≤ 30 s

The page polls, gets a state rebuilt from the rows, and is told one of a small set of things about its own stop only: not set off, on its way, a countdown, picked up, nobody there, or the bus has gone past. No coordinates cross the wire in either direction.

tripState · tripPayload · paintLive

Typical end-to-end latency is fifteen to twenty seconds; the worst case with a cold script is about forty-five. If the driver had no signal at the moment of the tap, the row is written whenever signal returns, carrying its original corrected timestamp.

What must always be true

Invariants

These are the properties the system is built to hold. They are the right things to attack: each one is load-bearing, and breaking any of them produces a failure that is quiet rather than loud.

1

Every tap is attributable to a named person

Only the driver the rota names for that route that Sunday, or his recorded cover, may write. Every other signed-in driver — including a coordinator — reads. This is the whole enforcement value of the record: on Monday, a row has a name against it.

2

A repeated tap does not become a second fact

Dedup is keyed event|stopId per run, server-side, under a lock. The client also merges forward-only: a background poll can add to local state but never remove what this phone has just recorded.

3

The driver's number reaches only a booked phone, on his route, on the day

Tracking is untied from booking on purpose — anyone may watch a stop without identifying themselves. The phone number is not. Watchers are given the coordinator's number instead.

4

Position is inferred, never tracked

GPS is used twice on the driver's phone: to stamp where a walkaround happened, and to lock the tap buttons while the wheels are turning. Neither leaves the device as coordinates. The passenger page has no geolocation code at all.

5

A check that could not be verified says so

A PIN entered with no signal lets the driver through and records the state as offline — never as ok. The record distinguishes "verified", "not asked" and "could not check", because on Monday those are three different facts.

6

Nothing is claimed that has not been recorded

The passenger page reports the record, not the road. It says "no pickup was recorded here" rather than "nobody was waiting", because a driver can forget to tap and the difference matters to the person standing at the kerb.

7

Losing signal costs nothing but time

Checks and taps queue locally and send themselves. Both apps open from cache. The only thing a passenger cannot get without a network is the bus's current position, which is the one thing that genuinely is not knowable offline.

8

A stopped bus cannot start a run

A walkaround with a critical defect blocks the trip. The app records and warns; it cannot immobilise a vehicle, and does not pretend to.

Security posture

Trust & privacy

State the model plainly, because it is unusual and a reviewer should judge it on its actual terms rather than against an assumed one.

What guards a write

A shared token, held in a public JavaScript file, checked by the script. Anyone who can load the driver app can read that token. It is not a secret; it is a speed bump that keeps casual traffic and crawlers out of the sheet.

Two things carry the real weight. Writes are constrained in shape — a tap must name a run, a route and a stop that exist, and passes through dedup — so the blast radius of a forged request is a wrong row in a tab a human reads every week. And the rota decides who may write what, so a valid token still does not let one driver tap another's route.

What identifies a passenger

A phone number, sent once by POST rather than in a query string, so it does not land in an address bar, a browser history, a referrer or Google's request log. The sheet stores the number and a salted SHA-256 fingerprint of it; the fingerprint is what the page carries afterwards. The salt is fixed and must stay fixed.

There are no passwords, no email addresses and no accounts anywhere in the passenger path.

What is deliberately public

The config file — driver names, roles, vehicle registrations, the endpoint, the token, the coordinator's number. It carries a standing instruction that nothing else goes in it: no PINs, no addresses, and no note explaining how any of it could be got round. Driver PINs live only in the sheet and are compared as one-way fingerprints.

Rate limiting

PIN entry locks after ten wrong tries for ten minutes. Identifying a phone is capped at twenty-five attempts in fifteen minutes. Both counters live in script properties.

Chosen, not inherited

Trade-offs

Polling, not push

Thirty seconds on the passenger page, sixty on the pre-cutoff gate, thirty on the driver's stop screen. Polling stops entirely when a page is hidden and resumes with an immediate fetch when it returns, so nothing polls from a pocket. Push would need a service and a subscription store; the cost is up to thirty seconds of staleness in a context where the bus itself is the slow part.

A spreadsheet as the database

Costs: no transactions beyond a script lock, row-scan reads, quota limits, and tabs a human can edit underneath the software. Buys: the coordinator can correct anything, the whole system is inspectable without tooling, and there is no hosting bill or migration to fail. The concurrency ceiling is two drivers.

Tracking untied from booking

Anyone may watch any stop without identifying themselves. This was a deliberate loosening after real people were locked out — booked on a laptop, walked out with a phone. It is safe because everything a watcher is told is a fact about a stop, and several households at one kerb already receive one identical answer.

One file per app

Roughly 300KB and 110KB of markup, styles and script in single documents. It reads badly and deploys perfectly: no build step, no bundler, no dependency tree, and the running artefact is byte-identical to the source. For a volunteer-maintained system with a five-year horizon, that trade was made knowingly.

Reasoning in the code, not in documents

Comments explain what went wrong before and why the code is shaped as it is — including the faults that produced each shape. Documents drift; a comment beside the line it explains is edited by whoever edits the line.

Most of these failed safe and silent. A wrongly-live button, a lockout that quietly stopped, a cache that quietly emptied. None would have generated a complaint. A review that only looks for loud failures will miss this system's characteristic fault.

Weakest points, named

Challenge these

Offered rather than defended. These are where a reviewer's time is best spent.

The trust model

A public token is the only credential between the internet and a write to the sheet. The mitigations are shape validation, rota-based authorisation and a human reading the tabs weekly. Is that proportionate for a system holding congregation phone numbers? Argue it either way.

Phone numbers at rest

The sheet stores both the number and its fingerprint. The fingerprint alone would not permit ringing a passenger back, which is a real operational need — but the number's presence is the largest privacy exposure in the system, and it sits in a Google Sheet governed by whoever holds the document.

Offset arithmetic

Lateness is computed at write time from a timetable string and a corrected timestamp, then bounded (45 minutes late, 12 early) to reject impossible values. Those bounds are judgement, not measurement. Test the boundaries, the midnight wrap, and British Summer Time transitions.

The single-writer assumption

One driver per route is assumed throughout, enforced by the rota rather than by the data model. A second phone signed in as the same driver is handled by dedup, but the design has never been stressed beyond two concurrent runs.

Service workers on iOS

Verified on desktop Chromium against localhost only. iOS Safari evicts worker caches after roughly a week of disuse, which may mean occasional passengers never get the offline benefit at all. Unproven in the field.

Human editing of the record

The coordinator can edit Trip Events by hand, and once cleared a row rather than using Undo, leaving arithmetic reading a gap. The software cannot prevent this and does not detect it. Whether it should is a fair question.

How it is checked

Verification

There is no CI. Verification is a set of standalone harnesses run against the real build before each release — no mocked application code, only a mocked network.

Two kinds

Browser harnesses drive the actual pages in mobile Chromium against a fake endpoint, and assert on what is on screen: the sentence a passenger reads, the number of tap buttons offered, whether a call button appears. Sandbox harnesses extract functions from the Apps Script source and run them against synthetic sheet data with a fake clock, so server logic is tested as itself rather than through an imitation.

What is covered

The live-run state machine; who may tap and who may only watch; mis-tap guards; the passenger's full set of states including the bus having gone past; offline behaviour for both apps; both service workers coexisting on one device; error wording across every failure path; theme contrast in four themes.

What is not

No real handset has ever been tested. The wake lock is exercised against a stand-in, not a real one. iOS is untested entirely. There is no load testing, and no formal accessibility audit beyond programmatic contrast checks.

The honest limit

The most recently found defect — a stop marked with a completion tick while the panel above it said the bus had gone past — was caught by looking at a screenshot. Not one assertion failed. The remaining risk concentrates in faults where every part is individually correct and the screen still says two things at once.
